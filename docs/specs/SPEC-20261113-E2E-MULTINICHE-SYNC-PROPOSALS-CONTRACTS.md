## 2. Requisitos EARS (Easy Approach to Requirements Syntax)

### R1 — Ingestao Omnichannel Canonica (`Wave 1`)
- **Ubiquitous:** O sistema SHALL canalizar capturas publicas de formularios Omni Builder, formularios `/f/$slug`, quiz/diagnostico, reservas/cotacoes turisticas, reservas de produtos CMS e propostas em classificados atraves de um unico servico server-side (`ingestOmnichannelLead`).
- **Event-Driven:** WHEN um visitante ou usuario autenticado enviar qualquer formulario, solicitacao de orcamento ou reserva de item anunciado em uma loja valida, THE system SHALL criar ou mesclar um registro em `leads_crm` (usando colunas validas `full_name`, `email`, `phone`, `destination`, `travel_start`, `travel_end`, `pax_*`, `custom_fields`) e vincular/atualizar `customers_crm` preservando todas as respostas dinamicas em `custom_fields`.
- **Unwanted Behavior:** IF `storeId` estiver ausente, invalido ou nao existir na base, THEN `ingestOmnichannelLead` SHALL retornar erro/skip seguro sem corromper outros tenants e sem mascarar falhas de validacao.

### R2 — Ponte Unificada de Campos Dinamicos & Catalogo CMS <-> Propostas (`Wave 2`)
- **Ubiquitous:** A biblioteca de dominio SHALL prover `@/lib/niches/unified-field-bridge.ts` normalizando atributos de produto/classificado, dados turisticos (`TravelPackageData`), `custom_inquiry_fields` e respostas de lead em um objeto canonico `UnifiedContextPayload`.
- **Event-Driven:** WHEN o colaborador abrir o editor de proposta a partir de um card Kanban ou do Workspace, THE editor SHALL pre-carregar dados estruturados do lead (`sourceListingId`, `customFields`, `paxList`, `clientDocument`, datas, passageiros) AND permitir selecionar qualquer pacote/anuncio real do catalogo CMS da propria loja (`products` + `classifieds`), preenchendo voos, hospedagens, roteiro, inclusos/exclusos, imagem e precificacao.
- **State-Driven:** WHILE `workspace.comercial.tsx` estiver ativo para lojas nao-turisticas, THE Kanban SHALL adaptar cartoes, etiquetas e criacao de orcamento pelo nicho SSOT da loja (`getUnifiedNicheSpec`) sem vazar vocabulario exclusivo de turismo.

### R3 — Compilador Universal de Contratos Tabulados & Renderizacao GFM (`Wave 3`)
- **Ubiquitous:** Todo contrato gerado a partir de Proposta de Viagem, Orcamento Multi-Nicho (`quotes`), Fatura Comercial, Pedido (`orders`), Negociacao (`deals`) ou Lead (`leads_crm`) SHALL compilar tabelas Markdown GFM estruturadas (`| Col | Col |`) para itens/servicos, especificacoes do nicho, cronograma/roteiro, passageiros/participantes, cronograma financeiro e campos personalizados, suportando escolha de template e secoes visiveis configuraveis.
- **Event-Driven:** WHEN um usuario visualizar contrato em `/workspace/contratos/novo`, `/workspace/contratos/$id/editor`, `/assinar/$token` ou `/contrato/$token`, THE `<ContractMarkdownRenderer />` SHALL renderizar tabelas semanticas HTML (`<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th>`, `<td>`) com classes de design tokens responsivas e zero pipes literais.
- **Safety / Integrity:** O endpoint `createContractFromProposal({ proposalId })` sem flags adicionais de customizacao SHALL preservar chamada atomica unica via RPC (`create_staff_travel_contract_from_proposal`) compativel com o contrato de seguranca P0 existente; a migration `20270405000000_e2e_multiniche_sync_tabular_contracts.sql` atualiza a propria RPC e permite fallback/customizacao explicita via `contract-compiler.functions.ts` para todos os nichos e orcamentos (`/workspace/orcamentos/$id`).

### R4 — Verificacao Adversarial & Gates (`Wave 4`)
- **Verification:** Toda funcionalidade SHALL ser provada com testes Vitest positivos e negativos (isolamento multi-tenant, entradas invalidas/nulas, falha de autorizacao, preservacao de campos dinamicos, idempotencia e renderizacao HTML de tabela GFM), alem de `npm run typecheck`, `npm run lint:design`, `npm run check:bff`, `npm run check:cycles`, `npm run check:schema`, `npm run check:migration-inventory`, `npm run check:tokens` e `npm run build`.
